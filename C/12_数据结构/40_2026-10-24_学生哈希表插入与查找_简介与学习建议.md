## 程序怎样组织数据

```c
typedef struct {
    int used;
    int id;
    int score;
} Entry;
```

每个 `Entry` 是一个哈希槽位：

- `used == 0`：空格，没有学生。
- `used == 1`：已经保存一条学生记录。
- `id`：学生学号，也是哈希表的键。
- `score`：学生成绩。

整张表是：

```c
Entry table[TABLE_SIZE];
```

`TABLE_SIZE` 是 10，因此合法下标是 `0～9`。

## 程序各部分的联系

### `hash`：决定从哪一格开始找

```c
int hash(int id) {
    return id % TABLE_SIZE;
}
```

取余结果作为起始下标。例如：

| 学号 | `id % 10` | 起始下标 |
| --- | --- | --- |
| 101 | 1 | 1 |
| 111 | 1 | 1 |
| 121 | 1 | 1 |
| 202 | 2 | 2 |

101、111、121 的起始位置都是 1，这就是哈希冲突。

### `initTable`：把所有槽位标成空

```c
table[i].used = 0;
table[i].id = 0;
table[i].score = 0;
```

真正决定“有没有数据”的是 `used`。把 `id` 和 `score` 清零是为了让未使用槽位有稳定的初始值，但不应该用 `id == 0` 代替 `used == 0` 判断空槽。

`main` 中 `Entry table[TABLE_SIZE] = {0};` 已经把整张表清零，随后又调用 `initTable`。两者有重复，但不会导致错误。初始化函数的价值是以后复用初始化逻辑时更清楚。

### `insert`：先找位置，再写入

```c
int start = hash(id);
for (int step = 0; step < TABLE_SIZE; step++) {
    int index = (start + step) % TABLE_SIZE;
    ...
}
```

插入最多检查 10 个位置：

1. 从 `start` 开始。
2. 槽位为空，可以直接写入。
3. 槽位已有同一个学号，用新成绩覆盖。
4. 槽位被其他学号占用，进入下一格。
5. 到下标 9 后通过 `% TABLE_SIZE` 回到下标 0。
6. 检查 10 格仍无空位或同号记录，返回 `0`，表示表满。

返回 `1` 表示插入或更新成功，返回 `0` 表示表满。

### 程序示例中的冲突轨迹

初始表全部为空：

| 操作 | 起始位置 | 实际位置 | 原因 |
| --- | --- | --- | --- |
| 插入 `101, 85` | 1 | 1 | 1 号为空 |
| 插入 `111, 90` | 1 | 2 | 1 号被 101 占用 |
| 插入 `121, 95` | 1 | 3 | 1、2 号都已被占用 |
| 插入 `202, 100` | 2 | 2 | 2 号仍为空 |

因此 121 最终在下标 3，查找时也沿同一条探测路径找到它。

### `search`：沿相同路径查找

```c
if (table[index].used == 0) {
    return -1;
}
if (table[index].id == id) {
    return index;
}
```

搜索从同一个哈希位置出发：

- 遇到目标学号，返回下标。
- 遇到空槽，返回 `-1`，表示没有这个学号。
- 遇到其他学号，继续检查下一格。
- 检查满 10 格仍未找到，返回 `-1`。

“遇到空槽就停止”在当前程序里成立，因为这里没有删除操作。线性探测表如果以后支持删除，不能直接把槽位清空，否则会截断后面的探测链，需要使用“删除标记”或重新整理数据。

### `main`：演示插入、查找和遍历

程序插入 101、111、121、202，再查找 121，最后遍历全部 10 格，只打印 `used == 1` 的有效记录。

## 已发现的输入边界

当前程序使用固定正学号，因此现有插入数据安全。扩展到通用输入时必须注意：

1. **负学号。** C 语言中负数取余可能得到负数，`hash(-1)` 可能返回 `-1`，随后作为数组下标会越界。通用版本应先将学号映射到 `size_t` 无符号范围，或明确拒绝负学号。
2. **成绩范围。** 当前 `score` 没有检查 `0～100`，非法成绩会被原样保存。
3. **学号 0。** `used` 已经负责判断空槽，所以学号 0 本身可以被表示，前提是业务允许。
4. **删除数据。** 当前不支持删除。若把 `used` 直接设回 0，后面的线性探测查找可能提前停止。
5. **容量固定。** 表满后插入返回 0；当前 `main` 会打印提示并结束，但还没有设计扩容。

这些问题没有在原始源码中修改，适合作为后续独立练习。

## 学习重点

1. **理解键和槽位的区别。** 学号 `id` 是查找键，数组下标是它在表里的位置，两者不是同一个数。
2. **理解哈希函数。** `id % 10` 只负责选择起点，不保证每个学号落在不同位置。
3. **理解冲突。** 不同键得到相同起点是正常现象，不是程序错误。
4. **理解线性探测。** 冲突后依次看下一格，到末尾后回到 0 格。
5. **理解 `used`。** 仅凭 `id` 或 `score` 判断空槽容易与有效数据混淆。
6. **理解插入上限。** 最多检查 `TABLE_SIZE` 次，确保冲突表满时能停止。
7. **理解查找依赖插入规则。** 插入和查找必须使用同一个哈希函数和同一个探测顺序。
8. **理解没有删除时，空槽可以终止查找。** 一旦支持删除，这条规则必须改。

## 学习难点

- 把学号 121 和数组下标 3 混为一谈。
- 认为 `101`、`111`、`121` 的哈希冲突是代码错误。
- 插入时只检查起始格，没有继续探测后面的空格。
- 探测循环没有次数上限，表满时可能无限绕圈。
- 更新已有学号时又插入一条重复记录，而不是覆盖原成绩。
- 查找时只看起始格，忽略之前冲突后移动过的数据。
- 判断空槽时使用 `table[index].id == 0`，而真正有效的状态字段是 `used`。
- 以为删除后直接把 `used` 清零也一定安全。
- 把固定表写成动态内存版本之前，没有先掌握基础线性探测流程。

## 零基础学习流程

1. **先画 10 个空格。** 标上下标 0～9，所有 `used` 都写 0。
2. **只算哈希起点。** 计算 101、111、121、202 的 `% 10`。
3. **手工插入 101。** 从下标 1 开始，发现空槽后写入。
4. **手工插入 111。** 从 1 开始，1 被占用，下一步到 2。
5. **手工插入 121。** 从 1 开始，依次排除 1、2，最后放入 3。
6. **手工查找 121。** 记录查找路径 1→2→3，确认与插入路径一致。
7. **运行程序。** 对照实际输出检查 121 和 202 的下标。
8. **测试不存在学号。** 在临时副本中调用 `search(table, 999)`，从哈希起点 9 出发，遇到空槽返回 `-1`。
9. **测试重复学号。** 再插入 `101, 99`，确认只会更新原槽位成绩，不新增记录。
10. **关闭源码重写。** 先写定义、哈希、初始化和插入，再补查找和遍历。

## 常见易错点与测试思路

| 测试操作 | 预期结果 | 检查目的 |
| --- | --- | --- |
| 插入 101、111、121 | 下标分别为 1、2、3 | 连续线性探测 |
| 查找 121 | 返回 3 | 沿冲突链查找 |
| 查找不存在的 999 | 返回 `-1` | 空槽终止 |
| 重复插入 101 并改成绩 | 更新 101 的记录 | 学号作为唯一键 |
| 填满全部 10 格后再插入新学号 | 插入返回 `0` | 表满检测 |
| 在临时版本中查找未填满时的空缺键 | 返回 `-1` | 正常未命中 |
| 调用 `hash(-1)` | 当前可能得到负下标 | 负数学号未处理 |
| 删除一个记录后直接清空 `used` | 后续搜索可能提前停止 | 删除标记风险 |

当前文件的内置示例已实际运行；表满、重复更新和不存在学号的函数级测试需通过临时测试程序验证，不能只凭源码推断成“已内置测试”。
